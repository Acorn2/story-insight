## 0. 执行摘要与决策

**目标**：让 Story Insight 在保持现有独立虚构故事及故事驱动文章写作质量、隐私边界和零运行依赖的前提下，为已完成的 Markdown 稿件**按需**生成封面、正文配图，并产出可供知乎、今日头条、百家号及微信公众号手动发布的图文素材。

**首选架构：同仓库、两个独立 Skill，最小桥接。**

- 继续保留 `.agents/skills/story-insight/` 作为独立、可复制的**纯写作 Skill**，不将实际生图设为写作任务的前置条件。
- 新建 `.agents/skills/story-visualizer/` 作为**视觉创作 Skill**；默认只接收**已完成并通过适用审校的对外稿件**，负责配图计划、封面、正文场景图、输出组装及生成记录。
- 给 `story-insight/SKILL.md` 增加**不改变现有默认行为**的可选交接说明：仅在用户明确要求配图/图文成品时调用视觉能力；仅选题、只审查、局部改稿仍在各自授权范围内停止。
- 视觉 Skill 支持 `plan-only`（无工具也可运行）、`cover-only`、`inline-only`、`full`、`rebuild-failed`。实际生图通过宿主提供的工具或可配置的独立生图后端完成。
- 正文始终不覆盖：视觉文件及带图副本写在原稿版本目录下的新子目录；既有 `outputs/` 仍由 `.gitignore` 忽略，不提交真实素材及结果。
- **MVP 不做**自动发布、热点抓取、真实人物复现、源连麦转图片、视频生成、复杂前端、数据库、通用图片搜索/爬取。

**为什么不直接把 `baoyu-article-illustrator` 全量复制进 `story-insight/SKILL.md`？** 它有自己的偏好初始化、选项确认、运行工具要求和生成文件流程；全量混入会增加写作上下文与运行耦合。应借鉴规划与输出机制、复用已经可用的后端，而不是让写作成功依赖某个供应商。

## 1. 已核验的仓库事实与本次新增范围

### 1.1 原项目当前事实（2026-10-30 读取 GitHub `main`）

| 维度 | 当前事实 | 对设计的约束 |
|---|---|---|
| Skill 入口 | `.agents/skills/story-insight/SKILL.md` | 必须保持原入口可独立复制/执行 |
| 创作阶段 | 分析与选题→写作/修改→阅读体验→文风→内容审校 | 图片放在**成稿后**，不反向重写故事 |
| 写作体裁 | 独立虚构故事、事实论证/直接解答、明确假设文章 | 不将事实文章自动当作虚构故事处理 |
| 输出 | `outputs/YYYY-MM-DD/议题/v01/`，正文 + `创作记录.md`，重做另存版本 | 图片在原稿版本下新增、并保留基线 |
| 现有配图 | 仅交位置、目的和提示词，标记“图片未生成” | 需要补全实际生图及成品组装 |
| 依赖 | 原 Skill 无 Python/Node、CLI、数据库或网页依赖 | 新增运行时必须是**可选且隔离**的 |
| 隐私 | 源连麦默认只用于内部议题理解；对外不得回放可识别个案 | 生图提示词与图像也遵循**同一对外边界** |
| 发布 | 所有文章为草稿，不自动发布 | 图文成品也是**待用户审阅的素材** |
| Git 忽略 | `.gitignore` 包含 `outputs/`、`.env`、`.env.*` | 不应将私密图片、API Key 加入仓库 |

本项目既有 `AGENTS.md` 还要求修改 Skill 后执行宿主可用的元数据校验，并通过真实产物检查；校验结果不等于文学质量或读者接受度通过。保持这项原则。

### 1.2 用户明确希望新增的能力

1. 输入一篇已经写好的故事或文章，不重新选题/写作；也支持明确授权后的“写作完成→自动配图”。
2. 生成能体现标题、情绪与核心悬念的封面图（与正文配图分开设计）。
3. 按**情节节点、人物选择、关系变化、场景转换**选出真正值得画的正文位置，不机械逐段插图。
4. 多张图尽可能统一画风、人物外观与关键物件；同一人物避免忽胖忽瘦、换脸或服饰失控。
5. 交付带图片引用的 Markdown 及独立图片文件，适合向不同自媒体平台复制上传。
6. 失败可重试、局部重画，不损坏成功图片和原稿；控制图片数量与调用成本。

### 1.3 范围与非目标

**P0/MVP 范围**：一篇文章、1 张封面、默认 2–4 张正文图、一个可用生图后端、计划-only 回退、可验收的文件交付；允许用户指定仅封面/仅正文及图片数。**平台适配先做预设与导出，不做发布端自动化。**

**暂不纳入**：自动配乐视频、自动登录平台、平台稿件发布、封面 A/B 运营分析、版权不明的图库下载、精确真人换脸、跨作品共享永久人物 IP、自动侵入其它项目读取原素材。

## 3. 产品交互与用户故事

### 3.1 使用方式

| 模式 | 触发语义 | 输入 | 输出 |
|---|---|---|---|
| `plan-only` | “先给这篇故事做配图策划” | 已完成 `.md` | 配图方案、角色/风格规则、prompt，明确图片未生成 |
| `cover-only` | “只补一张封面” | 一篇稿件 | 封面及生成记录 |
| `inline-only` | “给正文配三张图” | 一篇稿件 | 正文插图、带图副本 |
| `full` | “完成这篇文章的封面和正文配图” | 一篇稿件 | 封面 + 插图 + 图文副本 + manifest |
| `rebuild-failed` | “把失败的两张补生成” | 配图 manifest | 只重试失败任务，新版本存档 |
| `regenerate-selected` | “第 2 张图换成夜景” | 某图任务 | 只重画指定图片，保留其余产物 |

默认使用**用户已经明确提供的目标文章**。目录中有多个候选时，优先采用用户指定路径；不能确定目标时询问一个关键问题，而不是自行读取所有私人文章。

### 3.2 首选默认值（产品建议，不宣称各平台强制要求）

- 正文默认 `balanced`：长文目标 2–4 张；根据叙事必要性可以更少，甚至 0 张；用户要求的数量优先。封面独立计数。
- 画风默认 `editorial-cinematic`（克制的电影感插画），可选 `watercolor`、`realistic-illustration`、`minimal`、`ink`；**先验收画面风格，再决定是否加风格库**。
- 无需生成图中文字；封面采用**无字主图 + 留安全区**。标题可由用户在发布平台叠加；二期可选本地确定性字体合成，但绝不要求图像模型可靠拼写中文。
- 通用图片默认 16:9；可选宽幅或方形变体。**知乎、头条、百家号等平台实际封面比例、尺寸、大小及上传规则在发布时再核验，不能把此预设当平台官方规范。**
- 实际图片调用前，在 plan 中列出**图数、后端、分辨率及估计成本是否可获知**；成本无法核实时明确未知，不虚构价格。
- 用户已经请求生成完整图文且有可用工具时直接按范围执行；只在调用外部服务、发送有风险数据、费用或权限缺口未解决时暂停受影响的操作。

### 4.1 核心模块

**M1 - Input & Guard**：输入路径、体裁、是否已完成审校、用户授权、已生成文件状态；读取公开稿件即可，默认不读连麦原始材料及内部 `创作记录.md`。确需读取创作记录里的已有配图位置时只提取可公开的视觉信息，不能复制原案细节到请求或图像提示词。

**M2 - Scene Planner**：按文章的事实/虚构类型决定图像策略。虚构故事分析人物愿望、阻力、选择和后果；非虚构观点文章区分情景示意、概念图和数据类可视化，不把假设场景伪装成现场照片。

**M3 - Visual Bible**：统一画风、时间地点、主体、典型服饰、关键道具和禁项；单篇内共享。某个细节未在文章中确定时，可以设计**中性、非辨识性**视觉属性，但不得反向写进正文或暗示是现实事实。

**M4 - Cover Planner**：从故事的核心悬念/情感张力寻找一张具有辨识度的封面，图意可概括主题，但不得泄露人物结局、制造原文没有的惊险元素或误导事实。输出原比例母图和平台裁剪建议。

**M5 - Inline Planner**：选 2–4 个关键场景，记录每张的价值、准确插入锚点、人物状态、场景、构图与避免剧透要求；支持密度选项，但叙事价值优先。

**M6 - Render Adapter**：统一调用能力声明与返回格式，如 `provider/model/aspect_ratio/reference_support/output_path/error`。适配器可以是 Skill 对现有宿主工具的调用约定，不必一开始开发 Node/Python 包。

**M7 - Assemble & Validate**：从原文创建带图片引用的**新副本**，检查相对路径有效、图片文件真实存在、插图锚点唯一、图片顺序正确；失败保留纯文字正文并标注状态。

## 5. 配图智能规划规则（故事优先）

### 5.1 选择图像位置

可选高价值时刻：主角首次出场、关系的重要错位、关键动作、决定发生的瞬间、环境改变、重要道具改变含义、结尾余韵。**不能只因“到下一段了”插图。**

每个候选点用一个简单的**编辑判断**（不是固定评分门槛）：

- 该图能否帮助读者理解人物/空间/关键行为，或带来叙事气氛？
- 是否重复了近邻图片或直接把文字讲了一遍？
- 是否剧透下一步选择、虚构未写的事实、打断正在推进的段落？
- 画面是否可独立表达，能否在当前生图后端下稳定产出？

若不满足，就少配图；不要为了达到数量硬插。

### 5.2 封面与内图的不同目标

| 要素 | 封面 | 正文插图 |
|---|---|---|
| 核心目的 | 激发阅读兴趣、主题识别 | 补充空间、动作、人物关系或情绪变化 |
| 信息边界 | 不剧透，不以夸大取代吸引 | 严格以当前或此前已出现的信息作画 |
| 构图 | 主体清晰、强焦点、留裁剪与标题安全区 | 可多角色，但场景简洁、服务阅读节奏 |
| 文字 | MVP 不在图片内生成中文标题 | 原则上不嵌入文字 |
| 角色 | 可用剪影/背影/局部，避免误认真人纪实 | 尽量延续同一虚构角色视觉设定 |

### 5.3 人物与场景一致性

创建一个**角色卡**，只写文章支持或为视觉连续性所需的最小信息：`character_id`、年龄段（如有必要）、发型、衣着基调、固定道具、关系角色、不可改变特征、避免直接对应真人的限制。创建**场景卡**：时间、光线、地理位置的模糊级别、室内外、环境色温。

采用两级实现：

- MVP：同一 `Visual Bible` 和角色锚定短语注入全部 prompt；保留每张图的角色一致性检查结果。
- P1：仅在后端**确实支持**参考图传入时使用**已授权的虚构角色参考图**。若只有描述、没有参考能力，就如实报告“一致性为文字约束，不能保证跨图同脸”。不把真人原案照片作为默认参考。重试时优先复用已确认的参考图，避免无控制地让新生成图逐级传染偏差。

### 5.4 反幻觉与隐私边界

- 配图只能基于**可对外公开的当前文章**生成，不应将原连麦中的人物网络、罕见经历链、原话、主播、场次或现场细节引入 prompt、图片、文件名、alt 文案。
- 真实经历写作：生成的情境图必须表达“示意/插画”，不可表现为真实现场照片或匿名后真实人物肖像。
- 虚构故事：保留正文中的“虚构故事”标记；图片可以是虚构场景，但不得冒充真实采访证据。
- 不允许图像添加正文不存在的重要事件、伤情、指控、权力关系或者改变故事结局。
- 对未成年人、健康、私密关系、单方指控等敏感内容，避免逼真的特写与可识别标签；不能安全转化时跳过该图并记录理由。
- 不将内部 `创作记录.md`、源稿或 API Key 上传到非授权服务。第三方 API 输入默认视为外传行为，需说明并遵循用户给出的使用范围。

```text
│           └── privacy-and-review.md  # 隐私、事实、视觉审核
└── validation/
    ├── comparison-cases.md            # 保留原写作测试
    └── visual-acceptance.md           # 新增视觉验收案例、结果与限制
```

**遵守渐进式读取**：`story-visualizer/SKILL.md` 只保留任务路由和最重要边界，实际执行时再按需读 `references/`。这和原仓库的组织习惯一致。

### 6.2 一篇文章的产物（示例）

```text
outputs/2026-10-30/某故事/v01/
├── 知乎.md                       # 原文：永不原地覆盖
├── 公众号.md                     # 如存在，仍不修改
├── 创作记录.md                   # 内部记录，不拷贝到发布包
└── visual/
    └── zhihu/
        └── v01/
            ├── 配图方案.md
            ├── 视觉设定.md
            ├── manifest.json
            ├── prompts/
            │   ├── cover.md
            │   ├── inline-01.md
            │   └── inline-02.md
            ├── assets/
            │   ├── cover.png
            │   ├── inline-01.png
            │   └── inline-02.png
            └── 知乎-图文.md            # 仅新副本，引用 assets/ 相对路径
```

执行同一原文、同一平台的重新生成时新增 `visual/zhihu/v02/`。若源文章已经升级为 `v02`，新图文放在**源 `v02` 的 visual/** 下；避免跨正文版本错配。批量生产时每篇均生成独立 manifest 与素材包。若图片不适合公开同步，`outputs/` 下仍全部被 git 忽略。

### 6.3 manifest 最低数据模型（建议）

```json
{
  "schema_version": "1.0",
  "source_path": "../../../知乎.md",
  "source_version": "v01",
  "platform": "zhihu",
  "mode": "full",
  "provider": {"name": "unresolved", "model": null},
  "style": "editorial-cinematic",
  "status": "planned",
  "items": [
    {
      "id": "cover",
      "kind": "cover",
      "aspect_ratio": "16:9",
      "prompt_path": "prompts/cover.md",
      "output_path": "assets/cover.png",
      "status": "planned"
    },
    {
      "id": "inline-01",
      "kind": "inline",
      "anchor": {"section": "开头", "after_excerpt": "此处填写原文中唯一可匹配的短句"},
      "purpose": "建立人物处境",
      "aspect_ratio": "16:9",
      "prompt_path": "prompts/inline-01.md",
      "output_path": "assets/inline-01.png",
      "status": "planned"
    }
  ]
}
```

> 上面是**示例字段**，`source_path` 在实际实施时必须由程序/Agent **相对 manifest 所在目录计算**，不可照抄示例。可增加 `source_sha256`（有可用文件工具才算）、生成时间、成本/估算来源、重试次数、人工审核状态、错误信息。所有 `generated` 状态必须以**真实存在且可读取**的图片文件为依据。

图片状态：`planned`、`generated`、`failed`、`skipped`、`rejected`；总体 `status` 为 `planned`、`partial`、`generated`、`reviewed`、`blocked`。`generated` 不等于 `reviewed`，`reviewed` 不等于已获准发布。

## 7. 端到端工作流与错误处理

### 7.1 正常链路

1. **定位输入**：确认目标文章路径、体裁与本次任务范围。保留原稿及相应 `创作记录.md` 不变。
2. **准入检查**：稿件状态至少为可供配图的草稿，识别公开边界；若有未解决的严重事实/隐私阻碍，对受影响段落不生成图。
3. **读取正文并规划**：识别文章段落、叙事节点、人物设定；优先复用已有**可公开**配图建议，不能机械照单全收。
4. **产出方案**：为封面和插图生成位置、目的、构图、风格、画面信息/禁项；保存 `配图方案.md` 与 `视觉设定.md`。
5. **保存 prompt**：每张图单独保存版本化提示词，并记录关联正文的锚点；禁止只在聊天上下文里保存 prompt。
6. **探测后端**：检查当前实际可用的宿主生图工具/适配器、能否支持 16:9 和参考图、会不会发送到外部 API；无法生图则停在 `plan-only`，不创建虚假 PNG。
7. **实际生成**：MVP 默认顺序生成（封面→正文图）；成功图片检查后保存。失败单图重试有限次数，不影响其他项。
8. **质量检查**：图意与故事一致、跨图人物状态合理、无文字乱码、无遮挡/异常、无隐私复现或真人误导；必要时标记 `rejected` 并提供局部重画策略。
9. **组装**：为已生成且通过检查的正文图插入 Markdown 图片引用，写出独立 `*-图文.md`；封面以独立文件交付，**不强制作为首段大图插入正文**。
10. **交付**：输出真实生成数量、失败数、后端、已知费用/未知费用、文件位置、用户需最终审阅的事项；不宣布发布完成。

### 7.2 锚点插入策略

- 记录 `section`、`after_excerpt` 和上下文；优先以段落为基本插入单位，**不插入对白行内部、列表项内部或代码块内部**。
- 只有锚点在源文中**唯一匹配**、图片已存在且完成最低检查时才插入。若多处重复或段落顺序变更，标记 `needs_manual_anchor`，不得凭猜测插到错误位置。
- 组装不增删原文字句；允许在段落之间增加图片引用及必要图注。若有体裁/法律标注需保持原样。
- 失败的图片不插入，不放占位链接；保留 `配图方案.md` 方便后续补图。
- 如输入文章内容在配图后被修改，重新验证全部锚点及图意，不能静默沿用旧配图。

### 7.3 失败分支

| 场景 | 期望行为 |
|---|---|
| 无可用生图工具/无凭证 | 生成完整 plan/prompt；状态 `blocked`；不伪造图片 |
| API 调用失败 | 记录错误，不暴露密钥；限制重试次数；其他图继续 |
| 一张图角色漂移 | 标记 `rejected`；仅重画该图，其他图不动 |
| 锚点不唯一 | 保存图片与建议位置，但暂不自动插入 |
| 输入正文变化 | 阻止使用过期锚点；新建与新源版本对应的任务 |
| 费用/外传授权缺口 | 暂停需要服务调用的部分；计划生成仍可继续 |
| 仅封面任务 | 不擅自插正文图、不编辑正文 |
| 原稿仅局部审核 | 不把“局部审查通过”扩展为“整篇已通过审校” |

## 8. 配图提示词与质量规范

### 8.1 Prompt 契约

每张 prompt 包含：

```yaml
---
image_id: inline-01
kind: inline
source_article: 知乎.md
purpose: 建立人物与环境关系
aspect_ratio: "16:9"
character_ids: [protagonist]
scene_id: apartment_evening
spoiler_policy: no_future_event
negative: [source_identity, broadcaster_branding, illegible_text, fabricated_accusation]
---
```

正文采用结构化语义（不强制所有后端接受 YAML）：**画面主体 / 当下动作 / 情绪与光线 / 构图 / 风格规则 / 人物连续性 / 不可出现的内容**。外部供应商字段与宿主工具要求由适配层映射，不直接在写作规范里固定模型参数。

### 8.2 质量检查清单

- **关联度**：读者看到图片可以理解为什么出现在该段，不是通用图库配图。
- **叙事忠实**：图片没有新增重要人物关系、事件、罪名、疾病、灾难或原稿未出现的转折。
- **不剧透**：插入点之前未出现的信息，不提前透露给读者。
- **一致性**：同一人物年龄感、面貌、核心服饰、关键道具、画风尽量稳定；声明可控的局限。
- **视觉可用**：可打开、尺寸与比例合理，无严重变形、乱码、明显生成瑕疵、裁剪切断主体。
- **公众传播边界**：不包含原始私密素材标识、不暗示纪实或主播背书；有必要时保留虚构/示意说明。
- **交付可靠**：所有图片引用存在、路径正确，不附带 `创作记录.md` 或原连麦路径。

## 9. 技术选型与运行依赖隔离

### 9.1 MVP 推荐

| 层级 | 首选 | 备选/说明 |
|---|---|---|
| 内容分析 | 执行 Skill 的现有 Codex/大模型 | 不新增独立 NLP 服务 |
| 规划与管理 | 新增 `story-visualizer/SKILL.md` + references | 纯 Markdown 规则可运行 |
| 图片生成 | **先探测 Codex 环境中的原生 `imagegen`** | 若不存在，不宣称可用；再试已配置的 `baoyu-image-gen`/合法 API |
| 图像工具 | 宿主当前有的文件/图像工具 | 裁剪、压缩可选；不要设为基础依赖 |
| 后端适配 | 先文档化调用约定 | 一旦出现稳定的重复性需求，再引入薄脚本 |
| 数据存储 | Markdown + JSON manifest + PNG/JPG | 无数据库，无后端服务 |
| 运行时 | 原写作链路仍零依赖 | 只有启用某些生图后端时才可能需要 Bun/API/可用 CLI |

**依赖红线**：不能因为 `story-visualizer` 缺少 Bun 或 API Key 而导致 `$story-insight` 选题、写作、重写与审校不可运行。不要将第三方 Skill 的配置过程变成用户每次写作的默认步骤。

### 9.2 生图后端探测与选用

顺序建议：

1. 用户本次明确指定且当前可用的后端；检查费用与数据外传条件。
2. 当前宿主明确提供的可调用图像生成能力（例如某些 Codex 环境的 `imagegen`）。
3. 已配置并测试通过的 `baoyu-image-gen` 或等效后端。其 `codex-cli` 路线需要本地 Codex CLI 已登录且有相应权限；其 OpenAI API 路线需要独立 API Key。
4. 均不可用则**计划-only**，不将搜索到的图片链接冒充自生成结果。

后端能力表在第一次使用时记录：`supports_aspect_ratio`、`supports_reference_image`、`supports_batch`、`supports_output_file`、`auth_status`、`known_cost`。推荐只保留**一条已验证的 MVP 后端**；避免第一版支持十几个 API，维护成本高于业务价值。

### 9.3 平台适配（先打包，不自动发布）

| 平台 | MVP 输出 | 后续增强 |
|---|---|---|
| 知乎 | Markdown + 封面文件 + 正文场景图 | 适配上传接口、图像顺序与图注习惯 |
| 今日头条 | 通用图文稿和图片素材 | 发布前核验封面比例、正文插图和图片限制 |
| 百家号 | 通用图文稿和图片素材 | 发布前核验平台具体上传限制 |
| 微信公众号 | 通用图文稿和宽幅封面候选 | 二期接入专门 HTML/排版/发布工作流 |

不要在首期硬编码未经核对的各平台官方尺寸；同一篇文章可以针对不同平台生成**独立发布包**，但不应默认把同一个封面尺寸强行用于所有平台。正文图可以复用主题一致的原始图片，再按实际需求裁剪导出。

## 10. 交付给 Codex 的分阶段开发任务

### 阶段 A：隔离设计与 `plan-only` 最小可用

**任务**：新建 `story-visualizer` 的 SKILL 与 references；制作单篇文章的配图方案、角色设定、prompt 文件、manifest。更新 README/AGENTS/ARCHITECTURE/TECH-STACK 的边界说明，并最小化修改原 `story-insight/SKILL.md` 的可选交接。

**验收**：无图像工具也可以基于 `examples/` 合成故事生成完整规划；原有故事写作/审查路径没有被改变；真实连麦文件不会被读取或送入外部生图服务。

### 阶段 B：接入一个真实生图后端与图文组装

**任务**：只选本机真实可用的一种后端完成端到端；生成 1 张封面 + 2–4 张正文图，落盘后再按锚点组装副本；保存 provider、prompt、状态与错误。

**验收**：图片确实存在并可以打开；生成报告与实际图片数量一致；`*-图文.md` 中全部引用可解析；原稿不变。

### 阶段 C：人物一致性、重画与恢复

**任务**：增加视觉设定复用、参考图能力探测、单图重画、失败重试与正文版本变更检查。

**验收**：重画第 2 张不会重画第 1 张或封面；失败恢复不污染原始产物；所有版本可追溯。

### 阶段 D：多平台打包与多篇批处理（非 MVP）

**任务**：基于不同平台预设输出自包含素材包；支持按文件清单批量配图、单篇失败隔离、预算上限、批处理报告。

**验收**：单篇出错不影响其他文章；成本/数量上限生效；不自动发布、不提交私密结果。

## 14. 风险与后续决策

**风险 1：生图环境与账号混淆。** 本地 Codex 登录、宿主可用 `imagegen`、OpenAI API Key 是不同的能力/凭证；先做能力探测与一次小样。解决方案：`plan-only` 可独立完成，真实生图保留可替换后端。

**风险 2：人物一致性不可强保证。** 同一文字描述不足以确保同脸；有些后端不支持参考图。解决方案：角色卡 + 局部重画 + 实际视觉检查，不能保证就报告限制。

**风险 3：隐私与二次创作风险。** 原项目默认基于真人对话内部分析，但对外独立创作。图片比文字更容易让读者误认真实场面。解决方案：只传对外稿件、避免原人设/原场景复演、标注示意与虚构；视觉稿遵循同样的内容边界。

**风险 4：平台限制变动。** 不同平台的封面及素材规则会调整。解决方案：把尺寸视为导出预设；上线发布前再验证最新实际限制。

**风险 5：过度设计。** 不能为了增加配图把 Story Insight 做成通用多媒体 SaaS。解决方案：阶段 A/B 后先用真实作品评估“是否更愿意阅读、哪里视觉干扰、愿意花多少成本”，再决定是否做自动批处理。

**建议的下一步**：先完成阶段 A 的可运行配图策划模块，然后只用一篇**独立虚构故事**，试一次“封面 1 张 + 正文 3 张”的真实生图。确认图意、人物连续性、成本、隐私和图文稿可用后，再做多平台批处理。
